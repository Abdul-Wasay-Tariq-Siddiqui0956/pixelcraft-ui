WCAG 2.1 AA Foundations

Web Accessibility (a11y) Guide for HTML & CSS

Published by PixelCraft UI Editorial • 14 Min Read • Practical Standards

Accessibility is not an afterthought or an optional checklist. It is the fundamental practice of making the web usable for everyone, including people who navigate with keyboards, rely on screen readers, or experience low vision. Learn how standard HTML5 semantics and intentional CSS styling deliver exceptional accessibility without fragile JavaScript patches.

Why Is Semantic HTML the Best Accessibility Tool?

Native HTML elements (such as <button>, <header>, <nav>, and <main>) come pre-packaged with built-in accessibility semantics, tab focusability, and keyboard activation events recognized automatically by all major screen readers and operating systems.

1. Semantic HTML Landmarks

Screen reader users frequently navigate pages by skipping directly between major structural landmarks. Replacing generic <div> wrappers with HTML5 landmarks establishes a clear document hierarchy:

  • <header>: Identifies site branding, primary navigation, and global tools.
  • <nav>: Designates a collection of navigation links. Always supply an aria-label (such as aria-label="Main" or aria-label="Footer") when multiple <nav> elements exist.
  • <main>: Contains the central, unique content of the document. Every page must have exactly one <main> element.
  • <section>: Groups thematically related content with a dedicated heading (<h2>).
  • <article>: Encloses self-contained content that makes sense independently (e.g. a blog post or product card).
  • <aside>: Houses complementary, secondary content (e.g. sidebars or callouts).
  • <footer>: Marks copyright, colophon, and secondary directory links.

2. Visible Keyboard Focus (:focus-visible)

One of the most damaging mistakes on the web is writing outline: none; in CSS. This strips away visual indicators for keyboard users, making it impossible to tell which button or link is active.

Modern browsers support :focus-visible, which applies focus rings strictly when a user navigates via keyboard (or assistive tech) while keeping mouse clicks clean: 

/* WCAG 2.4.7 Visible Focus Ring */
:focus-visible {
  outline: 2px solid #6c5ce7;
  outline-offset: 3px;
}

The outline-offset: 3px; creates a breathing buffer so the outline never collides with or obscures the text inside the button.

3. Form Labels vs. Placeholder Text

Golden Rule of Form Accessibility

A placeholder is not a label. Placeholders disappear when a user types, provide low contrast by default, and are not reliably announced as labels by screen readers.

Always connect every form field to an explicit <label> element using matching for and id attributes: 

<!-- Accessible Form Control Pair -->
<div class="form-group">
  <label for="user-email" class="form-label">Email Address <span class="required">*</span></label>
  <input type="email" id="user-email" name="email" class="form-input" placeholder="you@university.edu" required />
  <span class="form-hint">We will send your assignment confirmation here.</span>
</div>

4. Color Contrast Ratios (WCAG 1.4.3)

The Web Content Accessibility Guidelines (WCAG) 2.1 Level AA require minimum contrast ratios between foreground text and background surfaces:

  • Normal Body Text (<18pt / <24px): Minimum 4.5:1 contrast ratio.
  • Large Text (≥18pt or ≥14pt Bold): Minimum 3.0:1 contrast ratio.
  • UI Components & Graphical Boundaries: Minimum 3.0:1 contrast ratio against adjacent surfaces.

In PixelCraft UI, our charcoal text (#171923) against canvas white (#FFFFFF) achieves an extraordinary 15.2:1 contrast ratio, effortlessly passing WCAG AAA standards.

5. Meaningful Image Alt Text

Every <img> tag requires an alt attribute. The content of that attribute depends on whether the image is informative or decorative:

  • Informative Images: Provide concise, contextual descriptions of the information conveyed (e.g., alt="PixelCraft UI components organized in a three-tier subscription grid").
  • Decorative Images: If an image or SVG is purely visual decoration and adjacent text already conveys the meaning, supply an empty alt attribute (alt="") or aria-hidden="true" so screen readers skip it cleanly.

6. Buttons vs. Links (Semantics Matter)

Element HTML Tag Proper Use Case Keyboard Trigger
Link <a href="..."> Navigating to a new page, document, or anchor hash. Enter key
Button <button type="button"> Triggering an action, opening a modal, submitting a form. Enter and Space keys

Never write <div onclick="..."> or <a href="#"> for button actions. Doing so breaks keyboard navigation and causes screen readers to misidentify interactive controls.

7. Common Accessibility Mistakes & Fixes

  1. Color as the Sole Indicator: Never signal state (such as error or success) using color alone. Always pair red or green highlights with clear text or explicit icons.
  2. Skipping Heading Levels: Do not jump from an <h1> directly to an <h4> merely for styling. Maintain a logical hierarchy (h1 → h2 → h3) and use CSS classes for visual sizing.
  3. Vague Link Text: Avoid generic links like "Click here" or "Read more". Use informative phrases like "Explore Navbar Components" or "Read the Responsive Design Guide".
  4. Trapping Focus: Ensure users can navigate into and out of all interactive controls using only the Tab and Shift+Tab keys.
